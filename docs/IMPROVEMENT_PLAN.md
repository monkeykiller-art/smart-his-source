# Smart HIS 项目改进方案

## 1. 目标与范围

本方案以当前 `main` 分支为基线，目标是把 Smart HIS 从“功能模块较完整的演示型微服务项目”提升为“可持续开发、可验证、可部署并具备医疗行业互操作能力的平台”。改进覆盖工程质量、安全与合规、数据治理、系统架构、临床业务、可观测性和交付运维。

## 2. 当前项目基线

Smart HIS 已采用 Java 21、Spring Boot 3.2、Spring Cloud、Nacos、PostgreSQL、Redis、Kafka、Flyway、MyBatis-Plus、HAPI FHIR R4、Prometheus 和 Kubernetes。代码按认证、网关、患者、临床、资源、运营、协同、药事、CDSS、DRG、急诊及平台等 13 个 Maven 模块拆分，业务覆盖面较广。

当前最需要补强的部分如下：

| 领域 | 当前观察 | 影响 |
| --- | --- | --- |
| 构建质量 | 在本地验证中，完整 Maven 测试尚未稳定通过 | 无法建立可靠交付基线 |
| 自动化测试 | 约 627 个 Java 文件，仅发现 2 个真正的测试类 | 回归风险高，模块边界缺少验证 |
| 持续集成 | 仓库中没有 GitHub Actions 工作流 | 提交无法自动执行构建、安全扫描和制品检查 |
| 数据迁移 | `his-patient` 同时存在两个 `V2` Flyway 迁移 | 新环境初始化可能发生迁移版本冲突 |
| 网关安全 | CORS 使用通配来源并允许凭据，`/actuator/**` 在白名单中 | 可能扩大跨域和运维端点暴露面 |
| 服务治理 | 13 个服务共享较重的 `his-common`，配置结构高度重复 | 服务耦合、升级成本和本地开发成本偏高 |
| 文档 | README 仅包含简要构建与启动命令 | 缺少架构、接口、数据、故障处理和贡献指南 |

## 3. GitHub 项目带来的参考

### 3.1 OpenMRS：稳定核心与模块化扩展

[OpenMRS Core](https://github.com/openmrs/openmrs-core) 将患者病历核心能力与可插拔模块分开，并提供 REST、FHIR 和开发者工具链。Smart HIS 可借鉴其做法，明确稳定领域模型、扩展接口和模块兼容策略，避免每个业务服务直接依赖不断膨胀的公共模块。

### 3.2 Ciyex：FHIR 原生的数据边界

[Ciyex EHR](https://github.com/ciyex-org/ciyex) 同样使用 Java 21 和 Spring 技术栈，并把 FHIR R4、患者、诊疗、预约、账单和多租户作为平台能力。Smart HIS 已引入 HAPI FHIR，下一步应从单一患者映射扩展为标准资源仓库、版本化能力声明、术语校验和互操作测试。

### 3.3 OpenHIS：完整医院业务闭环

[OpenHIS](https://github.com/tntlinking-opensource/openhis) 覆盖门诊、住院、医技、电子病历、药房药库、手术和结算。Smart HIS 的模块名称已覆盖多数领域，但需要用端到端场景证明跨模块闭环，例如“挂号—就诊—医嘱—收费—发药—归档”。

### 3.4 HospitalRun：弱网与易用性

[HospitalRun](https://github.com/HospitalRun/hospitalrun) 强调离线优先和医疗人员的操作效率。Smart HIS 的工作台可引入断网提示、请求重试、草稿自动保存、键盘操作和高频任务快捷入口，降低临床使用中的中断风险。

### 3.5 OpenEMR：安全治理与社区工程

[OpenEMR](https://github.com/openemr/openemr) 同时维护安全策略、贡献指南、API、Docker 和 FHIR 文档。Smart HIS 应建立安全漏洞报告流程、版本发布规则、升级策略和可复现的开发环境，让代码之外的治理能力成为项目的一部分。

## 4. 改进优先级

### P0：建立可信交付基线（第 1—2 周）

1. 修复完整构建和测试，使全新环境执行 `mvn clean verify` 能一次通过。
2. 将 `his-patient` 的重复 Flyway `V2` 文件重编号，并增加从空库升级的迁移测试。
3. 新增 GitHub Actions，在每次推送和拉取请求中执行编译、单元测试、集成测试、Spotless/Checkstyle、依赖漏洞扫描和制品构建。
4. 使用 Maven Wrapper 固定 Maven 版本，增加 `.java-version` 或工具链配置固定 Java 21。
5. 清理 `systemPath` 数据库驱动依赖，改为私有 Maven 仓库、受控安装脚本或供应商制品仓库。
6. 为数据库、Nacos、Redis、Kafka 增加一键启动后的烟雾测试，验证所有服务的 readiness 端点。

**验收标准：** 干净机器可按 README 在 30 分钟内启动；CI 连续 20 次通过；数据库迁移可在空库和上一版本数据库上成功执行。

### P1：补齐安全与审计（第 2—5 周）

1. 把网关 CORS 来源改为环境化白名单，禁止“凭据 + 任意来源”的组合。
2. 仅公开必要的健康探针，限制 Actuator、Swagger 和 Nacos 管理端访问。
3. 将 JWT 密钥、数据库口令和 Nacos 凭据接入 Kubernetes Secret 或 Vault，并实现密钥轮换。
4. 完善 RBAC：以机构、科室、岗位、患者关系和操作类型为授权维度，加入越权访问测试。
5. 建立不可篡改的审计事件，记录病历读取、修改、导出、处方、收费和权限变更；敏感字段不得写入普通日志。
6. 增加 SAST、依赖清单（SBOM）、镜像扫描和 secret scanning；建立 `SECURITY.md` 和漏洞响应时限。

**验收标准：** 高危依赖漏洞为零；核心接口均有授权与越权测试；敏感操作可按患者、用户和时间追溯。

### P1：构建分层测试体系（第 2—6 周）

1. 单元测试覆盖领域规则，包括处方剂量、库存扣减、费用计算、DRG 分组和急诊分级。
2. 使用 Testcontainers 验证 PostgreSQL、Redis 和 Kafka 集成，避免使用与生产行为不一致的内存替代品。
3. 为每个服务建立 API 契约测试；服务间调用采用消费者驱动契约，防止独立发布时破坏兼容性。
4. 建立五条首批端到端用例：患者建档、门诊就诊、住院入出院、处方发药、收费结算。
5. 对 FHIR Patient、Encounter、Observation、Condition、MedicationRequest 和 DiagnosticReport 增加结构、术语与 round-trip 测试。
6. 逐步设置覆盖率门槛：第一阶段行覆盖率 40%，核心领域 70%；后续根据缺陷数据提高。

**验收标准：** 所有业务服务至少有单元测试和接口测试；五条主流程可在 CI 中自动完成；核心领域变更必须由测试覆盖。

### P2：收敛架构与服务边界（第 5—10 周）

1. 盘点 13 个服务之间的调用和数据所有权，禁止跨服务直接读取对方数据库 schema。
2. 将 `his-common` 拆为轻量基础库、API 契约、事件契约和 FHIR 支持包，减少无关依赖传递。
3. 对本地开发提供组合式启动方式：按“基础服务、临床核心、运营扩展”分组启动，降低资源要求。
4. 定义 Kafka 事件命名、schema、版本、幂等键、重试和死信策略；采用 Outbox 保证数据库事务与事件发布一致。
5. 为同步调用加入超时、限流、隔离和熔断策略，并明确哪些流程允许降级。
6. 用架构决策记录（ADR）管理服务拆分、数据库选型、消息一致性和国产数据库兼容等关键决定。

**验收标准：** 每个服务有明确负责人、数据表、API 和事件清单；公共模块不再携带业务实现；关键事件可安全重放。

### P2：深化医疗标准与主数据治理（第 6—14 周）

1. 发布 FHIR CapabilityStatement，明确支持的资源、搜索参数、交互和版本。
2. 引入术语服务，统一 ICD、手术、药品、检验、科室和收费项目编码，并保存编码体系与版本。
3. 完善 EMPI 匹配、合并、拆分、冲突复核和操作审计，避免重复患者记录。
4. 增加 HL7 v2、FHIR Bundle 和批量导入适配层，为 LIS、PACS、医保和区域平台提供独立连接器。
5. 建立主数据变更审批、发布、生效和回滚流程；业务数据引用稳定标识，不直接依赖显示名称。
6. 对时间、时区、单位、金额精度、枚举和空值制定统一规则。

**验收标准：** FHIR 一致性测试通过；患者合并可回溯；外部系统接入无需修改核心领域代码。

### P2：提升临床工作台体验（第 8—16 周）

1. 以医生、护士、药师、收费员和管理员分别设计任务首页，减少跨模块跳转。
2. 支持病历草稿自动保存、冲突提示、签名后更正、常用模板和快捷键。
3. CDSS 提示按严重程度分级，记录采纳、忽略和原因，持续衡量误报率。
4. 为高频页面设定性能预算：首屏可交互小于 2 秒，关键提交在正常网络下小于 1 秒。
5. 增加无障碍、色彩对比、打印样式及常见分辨率适配。
6. 对移动查房和弱网环境提供只读缓存、排队提交或断点恢复能力。

**验收标准：** 五类角色完成主要任务的步骤数下降；关键页面性能达标；CDSS 提示效果有可量化数据。

### P3：可观测性、容灾与运营（第 10—18 周）

1. 在现有 Prometheus 指标上补充 OpenTelemetry Trace，并统一 trace ID、患者匿名标识和业务单号关联规则。
2. 为挂号成功率、医嘱执行延迟、库存异常、收费对账差异等业务指标建立仪表盘和告警。
3. 定义服务等级目标：核心接口可用性、P95 延迟、错误率和数据恢复目标。
4. 执行 PostgreSQL 备份恢复演练、Kafka 消息积压演练、单服务故障和机房切换演练。
5. 使用 Helm 或 Kustomize 管理环境差异，镜像使用不可变标签并支持自动回滚。
6. 建立容量模型，使用脱敏数据完成峰值门诊、批量结算和集中发药压测。

**验收标准：** 故障可由统一追踪定位；备份恢复达到既定 RPO/RTO；版本可在失败后自动或一键回滚。

## 5. 建议的首批交付清单

首个里程碑应控制在四周内，交付以下可验证成果：

1. 修复 Maven 全量构建和 Flyway 重复版本。
2. 上线 GitHub Actions，强制拉取请求通过构建、测试和安全扫描。
3. 为认证、患者、临床、药事和收费各增加一组单元测试与 PostgreSQL 集成测试。
4. 完成患者建档至门诊结算的第一条端到端测试。
5. 收紧 CORS、Actuator 和 Swagger 暴露范围，增加权限回归测试。
6. 扩充 README，并增加 `CONTRIBUTING.md`、`SECURITY.md`、架构图和本地故障排查手册。

## 6. 衡量指标

| 指标 | 当前基线 | 4 周目标 | 3 个月目标 |
| --- | ---: | ---: | ---: |
| `mvn clean verify` | 未稳定通过 | 稳定通过 | 小于 10 分钟 |
| Java 测试类数量 | 2 | 每个核心服务至少 1 组 | 核心领域覆盖率不低于 70% |
| 自动化端到端主流程 | 0 | 1 | 不少于 5 |
| CI | 无 | 构建、测试、依赖扫描 | 增加契约、镜像和部署验证 |
| 高危安全问题 | 未建立基线 | 完成扫描并清零 | 持续为零 |
| 关键接口 P95 | 未建立基线 | 完成测量 | 正常负载下小于 500 ms |
| 恢复演练 | 未发现记录 | 完成数据库恢复 | 每季度自动化演练 |

## 7. 实施原则

- 每项改进都以自动化验收条件结束，并与对应 Git commit、问题单和变更记录关联。
- 优先修复构建、测试、迁移和安全问题，再扩展新业务模块。
- 医疗数据模型、API 和事件均采用向后兼容的版本策略。
- 所有临床规则必须能说明来源、版本、生效时间和审批人，并可通过测试复现。
- 涉及患者隐私的数据默认最小化采集、最小权限访问、全程审计和加密存储。
